# Mission Forensics — Lamport Clock Incident Reconstruction

## Purpose

Mission Forensics is a deterministic distributed-systems lab for investigating a simulated thermal-alert incident across satellite processes. It demonstrates Lamport logical clocks, send/receive message timestamps, the happened-before relation, and the difference between physical timestamp order and causal order.

The simulation never changes operating-system clocks and does not claim that Lamport timestamps synchronize physical time.

## Scenario

The default incident is `INC-2048`, “Thermal Alert / Emergency Imaging”.

- SAT-01 records a thermal anomaly and sends `MSG-THERMAL-001` to SAT-03.
- SAT-03 records local process events, receives the alert, and sends `MSG-IMAGING-001` to SAT-05.
- SAT-05 receives the request, records readiness, and sends `MSG-ACK-001` to SAT-03.
- SAT-02 records an independent observation with no message path to the main incident chain.
- Fixed simulated physical timestamps deliberately place some receive records before their matching send records when sorted by wall-clock time.

## Lamport semantics

Each satellite has an independent integer counter.

- Local event: increment the owning process counter before recording the event.
- Send event: increment the sender's counter and copy the resulting logical timestamp into the message record.
- Receive event: update the receiver's counter to `max(local_counter, message_timestamp) + 1` before recording the receive event.

A receive request is rejected unless the referenced message has a recorded send, the selected receiver matches the message destination, and the message has not already been received.

## Causality

The event ledger records immediate predecessor IDs for:
1. the preceding recorded event in the same process, and
2. the matching send event for a receive.

The causality analyzer derives happened-before relationships through directed graph reachability. It does not compare Lamport timestamp numbers to infer causality.

If neither direction has a path, the API reports `NO_CAUSAL_PATH` and explicitly cautions that an incomplete trace does not prove concurrency.

## API

- `GET /api/algorithms/forensics/incidents`
- `POST /api/algorithms/forensics/incidents/thermal-alert/start`
- `POST /api/algorithms/forensics/replay/step`
- `POST /api/algorithms/forensics/replay/run`
- `POST /api/algorithms/forensics/events`
- `GET /api/algorithms/forensics/trace`
- `GET /api/algorithms/forensics/causality?event_a=E-002&event_b=E-006`
- `GET /api/algorithms/forensics/path/E-006`
- `GET /api/algorithms/forensics/report`

The backend broadcasts `FORENSICS_TRACE_RESET`, `LAMPORT_EVENT_RECORDED`, and `LAMPORT_TRACE_COMPLETED` using the existing WebSocket manager. The REST trace remains the recovery source.

## UI

Open `/mission-forensics` in the frontend. The workspace contains:
- Incident briefing and evidence list.
- Step-by-step replay with per-satellite lanes and event selection.
- Message/process edge visualization and clock transition inspector.
- Manual local/send/receive event controls.
- Pairwise happened-before comparison and ancestor/descendant analysis.
- Evidence report and JSON trace export.

The hero uses a remote Earth-from-orbit photograph as a decorative asset; the event data and algorithmic state are generated by the backend.

## Verification

Run the focused tests from the repository root:

```bash
python -m pytest tests/test_lamport_forensics.py -v
```

Build the frontend from its directory:

```bash
npm run build
```

Then run the full stack with Docker Compose and inspect `/docs` for the registered API endpoints. Do not report the tests or build as passing until they have been run in the target environment.
